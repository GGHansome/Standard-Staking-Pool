# V2 锁仓推荐质押池安全模型

## 1. 文档职责

本文档说明 V2 需要保护的资产、角色与信任边界、已确认的攻击路径、防护措施、失败边界和剩余风险。

- 产品承诺与退出行为见 [`product-spec.md`](./product-spec.md)。
- 状态机与调用顺序见 [`architecture.md`](./architecture.md)。
- 资金不变量与偿付公式见 [`accounting-and-solvency.md`](./accounting-and-solvency.md)。
- 可观测信号见 [`monitoring.md`](./monitoring.md)。

本文档不引入原始 V2 PRD 之外的新权限、暂停行为或经济规则。

## 2. 关键资产

### 2.1 用户本金

所有活跃仓位的 `amount` 汇总。本金只能通过用户关闭仓位退出；锁仓仓位提前退出时，最多按部署固定的 `penaltyRate` 扣除并转入 Treasury。

### 2.2 基础奖励

`baseRewardReserve` 对应的未支付基础奖励，包括尚未释放、已经归属但尚未支付，以及周期结束后等待回收的余额。

### 2.3 补贴备付金

`subsidyReserve` 对应的补贴现金，需要同时覆盖：

- 已确认但尚未支付的 `totalPendingSubsidy`；
- 尚未结算消化的 `unsettledMaxSubsidyLiability`。

### 2.4 奖励归属状态

包括仓位级 `pendingBaseReward`、`pendingInviteeBoostReward`、`pendingBoostReward`，以及用户级 `referralRewards`。这些状态即使尚未转账，也已经影响用户资产归属或潜在权益。

### 2.5 推荐关系

`hasSetInviter` 与 `inviterOf` 是永久状态。一旦首次质押完成，错误绑定或无上级选择都不能由用户修改。

### 2.6 奖励曲线历史

`rewardHistory` 决定锁仓到期时的奖励切分。错误快照或错误插值会影响锁仓加速奖励归属。

## 3. 角色与信任边界

### 3.1 普通用户

用户控制自己的质押、领奖和退出。用户不能修改活动参数、他人仓位或他人的推荐关系。

### 3.2 普通管理员

普通管理员可以注入新的基础奖励。系统不信任管理员传入的金额等于实际到账金额，必须通过转账前后余额差验证。

### 3.3 超级管理员

超级管理员可以：

- 分配或撤销普通管理员角色；
- 暂停与恢复合约；
- 修改 Treasury；
- 提取安全范围内的沉淀补贴；
- 在周期结束且空池后回收全部过期基础奖励；
- 救援非核心误转资产。

超级管理员不能通过 `recoverERC20` 提取 `stakingToken` 或 `rewardToken`，不能通过 `sweepSubsidy` 越过逻辑负债边界，也不能修改部署固定的经济参数。

现有规格没有确定管理员是否由 EOA、多签、时间锁或治理合约控制，也没有确定密钥轮换和失陷恢复流程。这些属于上线前仍需由部署与运营责任人确认的信任假设，不能由本文档补造。

### 3.4 Treasury

Treasury 接收提前解锁罚金。超级管理员可在活动期间和暂停期间修改该地址，因此用户信任当前超级管理员不会把未来罚金错误导向不可用或非预期地址。修改必须抛出事件供外部观测。

### 3.5 ERC20 Token

V2 只信任标准余额语义，不信任任意 ERC20 扩展行为。fee-on-transfer、rebasing、黑名单冻结、回调型或其他改变到账/支付语义的 Token 均不在支持范围内。

### 3.6 前端与索引器

链上合约是状态权威来源。前端或索引器显示错误不能改变用户资产，但可能误导锁仓选择、可领金额或罚金预期；因此必须使用聚合视图并正确处理只读到期投影。

## 4. 不可接受的结果

- 用户本金被基础奖励、补贴或管理员提取逻辑挪用；
- 已确认补贴负债或未结算最大补贴负债没有现金覆盖；
- 空池期间释放的基础奖励被后续首个用户获得；
- 未到期锁仓加速奖励被提前领取，或到期奖励因快照错误被错误作废；
- 已关闭仓位遗留不可领取的仓位级奖励；
- 推荐上级地址阻断下级的结算或领取；
- 暂停导致用户无法提取本金或领取已经可领的奖励；
- 核心 Token 被 `recoverERC20` 绕过资金桶规则提走。

## 5. 资金偿付攻击面

### 5.1 同币池资金桶混淆

**风险**：`stakingToken == rewardToken` 时，单一 `balanceOf` 同时包含本金、基础奖励和补贴，若按总余额计算可提取额度，可能挪用用户本金或奖励。

**防护**：

- 独立维护 `totalSupply`、`baseRewardReserve` 和 `subsidyReserve`；
- `sweepSubsidy` 只使用逻辑负债公式；
- `recoverERC20` 对核心 Token 完全禁用；
- 每次转账到账差只归属当前入口对应资金桶。

**剩余风险**：账本状态转换实现错误仍可能打破余额覆盖，必须通过不变量测试与运行监控发现。

### 5.2 补贴预算被提前提取

**风险**：只扣除已确认的 `totalPendingSubsidy` 会忽略已释放未结算和未来尚未释放的潜在补贴，使管理员过早提取备付金。

**防护**：

- 同时维护 `unsettledMaxSubsidyLiability`；
- `maxSweepableSubsidy()` 同时扣除两类负债；
- `sweepSubsidy` 先同步全局账本，再计算额度；
- 有 TVL 时不因时间流逝自动释放潜在预算。

### 5.3 多次小额注入取整套利

**风险**：逐笔计算并向下取整补贴预算时，管理员可把注入拆成多笔小额，使预留总额低于理论最大支出。

**防护**：按 `injectedBaseCumulative` 的累计量差值计算新增预算；消化侧同样按 `settledBaseCumulative` 累计重算。

### 5.4 Leftover 重复计提或漏计

**风险**：续奖时将旧周期未释放奖励既当作新注入再次预留，又纳入新曲线，造成重复扣款；或完全忽略旧余额，造成释放曲线丢失。

**防护**：

- 新曲线使用 `actualBaseReward + leftoverBaseReward`；
- `injectedBaseCumulative` 只增加本次 `actualBaseReward`；
- `leftoverBaseReward` 不重复增加基础奖池和补贴预算。

### 5.5 小额奖励永久锁定

**风险**：新调度总额不足以形成非零 `rewardRate`，Token 已进入合约却无法通过水位线释放。

**防护**：`notifyRewardAmount` 必须拒绝无法形成非零速率的金额。

### 5.6 过期基础奖励尾差

**风险**：周期结束后的取整尾差或无人领取余额长期占用 `baseRewardReserve`，并继续占用对应补贴预算。

**防护**：只有周期结束且 `totalSupply == 0` 后，超级管理员才可通过 `sweepExpiredBaseReward` 一次性回收全部剩余基础奖励，并同步增加 `settledBaseCumulative`。

## 6. 用户退出与锁仓边界

### 6.1 提前解锁

提前解锁始终允许，避免本金永久锁定。安全结果为：

- 罚金按 `floor(amount * penaltyRate / BPS)` 计算且不超过本金；
- 罚金实时转入当前 Treasury；
- 基础奖励和自身推荐补贴正常支付；
- 未解锁锁仓加速奖励作废，只减少已确认补贴负债，不减少补贴现金。

当 `penaltyRate == BPS` 时，用户本金退还额为 0，这是允许的部署配置。前端需要清晰展示，但合约不得因零退还额破坏关闭流程。

<a id="暂停期间退出"></a>

### 6.2 暂停期间退出

暂停只阻止新增质押、奖励注入和管理员资金回收，不阻止：

- `withdraw`；
- `withdrawMultiple`；
- `claimAll`；
- `exit`。

奖励时间和仓位到期继续推进。该边界保证前端宕机或紧急暂停时用户仍可直接退出。

### 6.3 关闭仓位遗留奖励

**风险**：先销毁仓位再处理 pending 状态，会造成基础奖励、自身推荐补贴或已解锁锁仓加速奖励永久不可领取。

**防护**：关闭前先完成结算与支付，再把 `amount` 置 0 并移出活跃数组。

## 7. Gas 与拒绝服务

### 7.1 活跃仓位遍历

`updateReward(user)` 需要遍历用户全部活跃仓位。攻击者可以创建大量微小仓位放大自身交互 Gas，或使聚合操作无法执行。

防护边界：

- 每个用户最多 `MAX_ACTIVE_DEPOSITS = 50` 个活跃仓位；
- 关闭时 Swap and Pop，以 O(1) 移除；
- 批量提取数组有长度上限；
- 单笔 `withdraw` 始终提供精确关闭路径。

50 是 V2 接受的版本级上限；若未来修改，必须重新编译并同步 Gas 与测试验收口径。

### 7.2 推荐返佣直接转账 DOS

**风险**：若下级结算时直接向上级转账，上级 Token 接收异常或外部行为可能阻断下级交易。

**防护**：推荐返佣只写入 `referralRewards`，由上级后续主动 `claimAll`。三级计算固定为有限次数，并按连续前缀短路。

### 7.3 批量提取部分成功

**风险**：某个仓位失败但其他仓位已关闭，会使前端与链上状态难以一致恢复。

**防护**：`withdrawMultiple` 全有或全无；任何无效、非本人、已关闭、重复 ID 或长度违规都使整笔交易回退。状态更新完成后再执行聚合转账，并按仓位逐笔抛出事件。

## 8. 推荐关系安全

### 8.1 自我邀请与无效邀请

首次绑定拒绝零地址以外的无效邀请人和用户本人。显式传入 `address(0)` 则永久选择无上级，不允许后续补填。

### 8.2 环形关系

关系满足：

- 每个地址只完成一次邀请状态绑定；
- `inviterOf` 永不改写；
- 新用户只能绑定已经完成绑定的地址。

因此新用户绑定时不可能已是既有邀请链的祖先，结构上不能形成环，不需要运行期环检测。

若未来引入改绑或换上级能力，该不变量不再成立，必须重新设计环检测和历史奖励归属。该未来能力不属于 V2。

### 8.3 女巫与小号套利

用户可以使用自己控制的其他地址形成推荐关系。现有产品决定把这种行为视为可接受的经济博弈，因为补贴只随真实质押产生的基础奖励计提，系统同时获得真实 TVL。

该决定不等于具备身份级女巫防护，也不证明所有运营地区都接受该增长方式。若未来要求按真实身份限制推荐，需要新的产品、隐私、合规和架构决策。

## 9. 奖励周期与空窗

### 9.1 空池奖励抢占

`totalSupply == 0` 时全局水位线不增长，期间释放的基础奖励自然流失，不能在后续首个用户入池时补发。

全局同步必须同时减少 `baseRewardReserve`、增加 `settledBaseCumulative` 并重算潜在补贴负债，避免“奖励不归用户但资金和负债仍被占用”的账本分裂。

### 9.2 非奖励期创建锁仓

首次注入前或周期间空窗，活期仓位可创建，锁仓仓位必须回退。该限制避免用户在没有有效基础奖励释放时承担锁仓承诺。

### 9.3 锁仓期超过奖励周期

合约不保证整个锁仓期都有奖励。当前周期结束后若未续奖，基础奖励和加速补贴停止；如果到期前续奖，原仓位继续按固定 `boostRate` 计提。

风险由前端提示而不是合约阻断。用户仍承担锁仓或提前退出规则。

## 10. Token 兼容与资产救援

### 10.1 实际到账校验

`stake`、基础奖励注入和补贴补缴都必须分别比较转账前后余额差。实际到账与传入金额不一致时回退 `FeeOnTransferNotSupported()`，不按实际到账降级记账。

同币池必须在每次 `safeTransferFrom` 周围就地取差，不能复用全局余额快照。

### 10.2 非标准 Token

fee-on-transfer、rebasing、黑名单冻结和回调型 Token 可能破坏以下假设：

- 输入金额等于资金桶增加量；
- 支付金额等于用户实际收到量；
- 合约余额只因显式转账变化。

V2 明确不支持这些 Token，不为其提供适配或偿付兜底。

### 10.3 Recover 边界

`recoverERC20` 只救援非核心误转资产，必须禁止：

- `stakingToken`；
- `rewardToken`；
- 任何属于本金、基础奖励、补贴或罚金处理中间余额的核心资产。

同币池的核心 Token 完全不能通过 `recoverERC20` 转出。沉淀补贴只能走 `sweepSubsidy` 的负债校验路径。

## 11. 快照与插值安全

### 11.1 奖励周期边界

插值必须按快照保存的 `periodFinish` 截断，防止把奖励结束后的零释放时间平均进入锁仓期。

### 11.2 无右侧真实快照

最后一个真实曲线折点之后首次结算到期仓位时，使用虚拟当前节点。虚拟节点不写历史，避免到期结算本身制造新的曲线折点。

### 11.3 同时间戳与空数组

- 命中 `time == unlockTime` 直接返回，避免分母为 0；
- `rewardHistory` 为空时返回当前 `rewardPerTokenStored`；
- 同区块多次改变曲线时覆盖最后一条快照。

### 11.4 历史增长

V2 不裁剪 `rewardHistory`。长期存储增长是为保持结算确定性和实现边界简单而接受的代价。写入只发生在真实曲线变化入口，`claimAll` 不写快照。

## 12. 输入与地址校验

必须拒绝：

- `stake`、`notifyRewardAmount`、`recoverERC20` 的零金额；
- 无法形成非零 `rewardRate` 的奖励注入；
- 零 `rewardsDuration`；
- 零 `stakingToken`、`rewardToken`、`admin`、`treasury` 等核心地址；
- 超出配置边界的锁仓、推荐、补贴上限和罚金参数。

地址错误与数量错误使用不同错误语义，避免调用方错误处理混淆。

## 13. 剩余风险与未确立事项

现有 V2 功能基线接受或尚未解决：

- 超级管理员的具体托管方式、审批、时间锁和密钥恢复流程未定义；
- `rewardHistory` 长期增长带来的存储成本；
- 单用户最多 50 个仓位的最坏 Gas 需要在目标链环境验证；
- 推荐小号行为被经济模型接受，不提供身份级女巫防护；
- 目标链、目标司法辖区和多级推荐的合规结论未定义；
- 监控责任人、告警阈值和应急升级路径尚未确定，见 [`monitoring.md`](./monitoring.md)。
